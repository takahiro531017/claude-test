# セキュリティ設計書

日本の個人情報保護法(安全管理措置)の考え方に沿った設計の整理です。法的な適合性の最終判断は、自社の個人情報保護の責任者・専門家(弁護士等)に確認してください。
本書の内容は実装と対応しており、権限の根拠は `supabase/migrations/` と、それを検証する `supabase/tests/10_rls_test.sql` です。

## 1. 取り扱う個人情報と最小化

| 区分 | 項目 | 取り扱い |
|---|---|---|
| エンドユーザー(要配慮度の高い順) | 氏名・電話番号・住所 | **任意入力**(販売店経由で足りれば入力しない運用)。暗号化して `repair_pii` に保存。一覧用に**マスク値**のみ `repairs` に保存 |
| 販売店の担当者 | 担当者名・連絡先 | 業務上の連絡先。平文で保存(保持期間経過後に削除) |
| 従業員 | 氏名(表示名)・メール | 認証・操作記録のため保持 |

- 平文のエンドユーザー情報は、**DBにも、ログにも、URLにも、ブラウザの localStorage/sessionStorage にも残しません**(E2Eテストで確認。ESLintで `localStorage`・`console` の使用を禁止)。
- 保持期間(既定:完了後3年)を過ぎた個人情報は自動で削除(匿名化)します。

## 2. 権限表(DBのRLSで強制)

画面で非表示にするだけでなく、**DBが拒否します**。なお、MFA(aal2)を通過していないセッションは、全ロールで「何も見えない・できない」です。

| 操作 | admin | hq_viewer | branch_staff | branch_viewer |
|---|---|---|---|---|
| 案件の閲覧 | 全拠点(削除済み含む) | 全拠点 | 自拠点のみ | 自拠点のみ |
| 案件の新規登録 | 全拠点 | × | 自拠点のみ | × |
| 案件の更新・ステータス変更 | ○ | × | 自拠点のみ | × |
| 論理削除 | ○ | × | 自拠点のみ | × |
| 復元(論理削除の取消) | ○ | × | × | × |
| 物理削除 | ○(のみ) | × | × | × |
| 完了/キャンセルの取消 | ○ | × | × | × |
| 個人情報の平文表示 | ○(監査) | ×(常にマスク) | 自拠点のみ(監査) | ×(常にマスク) |
| 個人情報の入力・更新 | ○ | × | 自拠点のみ | × |
| 写真・添付の閲覧 | 全拠点 | 全拠点 | 自拠点 | 自拠点 |
| 写真・添付の追加/削除 | ○ | × | 自拠点のみ | × |
| CSV出力 | ○(個人情報列も可・明示指定時のみ) | ○(個人情報列なし) | 自拠点のみ(個人情報列なし) | × |
| マスタ・設定の変更 | ○ | × | × | × |
| ユーザー招待・権限変更・MFA再設定 | ○ | × | × | × |
| 監査ログの閲覧 | ○(閲覧のみ) | × | × | × |

補足
- 他拠点の案件は参照できません(「管理番号の完全一致のみ参照」は**採用していません**)。ただし、受付時の二重登録防止のため、「同一シリアルが他拠点に存在するか(はい/いいえ)」だけは返します(詳細は返さない)。
- 管理者を含め、**ブラウザ(DBクライアント)から暗号文テーブル `repair_pii` は直接読めません**。平文化は必ず Edge Function `pii-reveal` 経由です。
- ステータス遷移の規則(1段ずつ前進/差し戻し、完了の取消は admin のみ)は DB トリガーで強制します。管理番号・拠点・作成者は変更不可、`version` はクライアント指定を無視してサーバーが採番します。

## 3. 認証・セッション

| 項目 | 実装 |
|---|---|
| 登録 | **自己登録不可**(`enable_signup=false`)。admin が招待(Edge Function `admin-users`) |
| パスワード | 12文字以上、英大小文字・数字・記号(`config.toml`) |
| MFA | **TOTP 必須**。(1)画面側で未通過なら先へ進めない (2)**DB側でも**JWTの `aal2` でなければ全ポリシーが拒否 (3)Edge Function も `aal2` 必須 |
| ブルートフォース | Supabase Auth のレート制限(`config.toml [auth.rate_limit]`)。ログイン失敗メッセージは理由を区別しない |
| セッション | 無操作30分で自動ログアウト(設定可)。トークンは `sessionStorage`(タブ限定)に保持し、`localStorage` は不使用。Pro以上では Supabase 側の `inactivity_timeout` も併用可 |
| 無効化 | `profiles.active=false` で即時に全データが見えなくなる(JWTが有効でもRLSが拒否) |

## 4. 個人情報の暗号化

- 方式: **AES-256-GCM**(認証付き暗号)。Web Crypto API。項目ごとにランダムな96bit IV。
- **AAD(追加認証データ)に `案件ID:項目名` を束縛**しています。暗号文を別の案件・別の項目へコピーしても復号に失敗します(改ざん・差し替え対策)。
- 保存形式: `v<鍵番号>:<IV>:<暗号文+認証タグ>`(`repair_pii.name_enc/phone_enc/addr_enc`)。
- **鍵はDBと別管理**: Edge Function のシークレット(`PII_KEYS`, `PII_KEY_CURRENT`)にのみ存在。DBのバックアップやSQLダンプには含まれません。DBが漏れても鍵がなければ復号できません。
- 暗号化・復号はサーバー側(Edge Function)でのみ実行。平文はメモリ上のみで、ログに出しません(エラーログにも例外内容を出さない)。
- 一覧用のマスク値(`山田 ○○`、`090-****-1234`)は暗号化前にサーバーで生成して保存します。

### 鍵の管理
- 生成: `openssl rand -base64 32`(README の手順)。生成した本人以外にも見えない形で、**会社の金庫に2名以上がアクセスできるよう保管**。
- 保管場所: ①Supabase の Edge Function シークレット ②会社のパスワード管理(金庫)。**メール・チャット・Gitには置かない。**
- **鍵を失うと個人情報は復元不可能**です(これは暗号化の性質であり、意図した設計です)。

### 鍵のローテーション(年1回、または漏えいの疑い時)
1. 新しい鍵を生成し、**旧鍵を残したまま**鍵番号2として追加:
   ```bash
   supabase secrets set PII_KEYS='{"1":"<旧鍵>","2":"<新鍵>"}' PII_KEY_CURRENT=2
   ```
   (以降の新規書込は鍵2。既存データは鍵1のままでも読めます)
2. 全データを新しい鍵で再暗号化(まずドライラン):
   ```bash
   SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... PII_KEYS='{"1":"..","2":".."}' PII_KEY_CURRENT=2 node scripts/rotate-pii-key.mjs
   ... node scripts/rotate-pii-key.mjs --apply
   ```
   途中で止まっても再実行して安全です。完了メッセージの「再暗号化が必要」が 0 になるまで繰り返す。
3. **直前のバックアップ(旧鍵で暗号化された個人情報を含む)の保持期限が切れるまで、旧鍵は破棄しない**。不要になったら `PII_KEYS` から旧鍵を除き、金庫の旧鍵も廃棄する。
4. 実施日・担当・理由を記録する。

## 5. 画面での個人情報の扱い

- 一覧・ダッシュボード・カンバン: マスク値のみ。
- 詳細: 「表示する」を押した時だけ平文。**押す前に監査ログへ記録**し、記録できない場合は表示しません。60秒で自動的に非表示。
- 大量閲覧の抑止: 同一ユーザーが10分間に30回を超えて表示しようとすると拒否(HTTP 429)。
- 預り証(印刷)にはエンドユーザーの個人情報を載せません。
- CSV: 個人情報列は既定で除外。含められるのは admin が確認ダイアログを経て明示指定した場合のみ。出力操作(件数・個人情報の有無・絞り込み条件)は監査ログに記録。CSVの数式インジェクション(`=`,`+`,`-`,`@`始まり)は無害化。

## 6. 監査ログ

| 記録する操作 | 内容(値は記録しない) |
|---|---|
| ログイン・ログアウト | 誰が・いつ |
| 作成・更新 | 案件の管理番号、**変更された項目名のみ**(値は記録しない=個人情報を監査ログに残さない) |
| ステータス変更 | 変更前→変更後 |
| 個人情報の閲覧(表示)・更新 | 誰が・どの案件を・いつ |
| CSV出力 | 件数、個人情報の有無、絞り込み条件 |
| 論理削除・復元・匿名化 | 誰が・どの案件を |
| 権限変更・ユーザー招待・MFA再設定 | 対象ユーザー、変更後の権限 |

- **追記専用**: `UPDATE/DELETE/TRUNCATE` は DB トリガーで拒否(スーパーユーザーでも)。クライアントには `INSERT` 権限も与えず、記録はトリガーと `service_role` 限定の関数のみ。
- **改ざん検知**: 各行に直前行のSHA-256ハッシュを連鎖(`prev_hash`/`hash`)。管理画面「改ざんチェック」(`verify_audit_chain()`)で検証。トリガーを外して行を書き換えた場合でも検出できることをテスト済み。
- 閲覧は admin のみ。
- **限界**: ログイン/ログアウトの記録はブラウザから送信されるため、改造されたクライアントでは省略され得ます(Supabase Auth 側のログでも確認可能)。DBの管理者権限(Supabaseの組織オーナー/DBパスワード保持者)を持つ人は、ハッシュ連鎖ごと再計算して書き換えることが理論上可能です。外部への定期エクスポートで補強してください(運用マニュアル)。

## 7. Webアプリ・通信の対策(OWASP観点は `セキュリティ自己点検.md`)

- HTTPS強制・HSTS・CSP・`X-Frame-Options: DENY`・`nosniff`・`Referrer-Policy: no-referrer`(`vercel.json` / `public/_headers` / `deploy/nginx.conf.example`)。
- XSS: Reactの自動エスケープのみ使用(`dangerouslySetInnerHTML` 不使用)、CSPで外部スクリプト不可。
- CSRF: 認証はCookieではなく `Authorization: Bearer` ヘッダ。Edge Function は `ALLOWED_ORIGIN` のみCORS許可。
- SQLインジェクション: PostgREST/Supabaseのパラメータ化クエリ。検索語は記号を除去してから `or()` フィルタに渡す(注入できないことをE2Eで確認)。
- 入力検証: DBの `CHECK` 制約(長さ・値域・列挙)+Edge Functionでサーバー側検証。クライアント側の検証だけに頼らない。
- ファイル: 画像(JPEG/PNG/WebP)とPDFのみ、1枚10MBまで。**(1)クライアントで種類・サイズ・マジックバイト確認 (2)Storageバケットで MIME・サイズ制限 (3)非公開バケット+5分の署名付きURL**。ウイルススキャンは未実装(§9)。
- シークレット: 環境変数/Supabaseシークレットのみ。`.gitignore` と CI の gitleaks で混入を防止。フロントに埋め込むのは公開前提の anon キーのみ(RLSが守る)。`service_role` キーはEdge Function内のみ。

## 8. バックアップ

日次・暗号化(age)。手順と復元訓練は `運用マニュアル.md §4`。バックアップには暗号文のみが含まれ、**復号鍵は含まれません**。

## 9. 既知の制限・残リスク

1. **ウイルススキャン未実装**: 画像/PDFのみに制限しマジックバイトも検査していますが、PDF内の悪性コードまでは検査しません。必要なら Storage の Webhook から ClamAV 等に連携してください(未実装)。
2. 個人情報を**表示した人が画面を撮影・書き写す**行為は技術的に防げません。教育・規程・監査ログによる抑止です。
3. 監査ログのログイン記録はクライアント送信(§6)。DB管理者による書き換えは外部エクスポートで補強。
4. セッションの強制失効は、Supabase のセッション設定(Pro以上)に依存する部分があります。
5. 実環境(Supabase)での通し検証は未実施(`要件充足チェック表.md`)。

# 運用マニュアル(システム管理者向け)

対象: 本社の情報システム担当(`admin` ロール)。Claude などのAIツールがなくても、この手順だけで運用できます。
前提: 本番構築は [README.md](../README.md) の手順で完了していること。

---

## 1. ユーザーの追加・変更・削除

### 追加(招待)
1. 管理者でログイン → 画面上部「管理」→「ユーザー」タブ。
2. メールアドレス・表示名・権限・所属拠点を入力して「招待する」。
3. 本人に招待メールが届きます。リンクを開く → パスワード設定(**12文字以上**)→ 認証アプリでMFA登録、の順に進むよう本人へ案内してください。
   - 招待リンクの有効期限は短いです。切れた場合は Supabase ダッシュボード → Authentication → Users で該当ユーザーを選び「Send invitation / Send password recovery」を再送します。

| 権限 | 用途 | 所属拠点 |
|---|---|---|
| 管理者(admin) | 本社情シス。全操作・マスタ・ユーザー・監査ログ | 不要 |
| 本社閲覧(hq_viewer) | 全拠点の閲覧のみ(個人情報は常にマスク) | 不要 |
| 拠点担当(branch_staff) | 自拠点の閲覧・登録・更新・個人情報の表示 | 必須 |
| 拠点閲覧(branch_viewer) | 自拠点の閲覧のみ(個人情報は常にマスク) | 必須 |

### 権限・拠点の変更(異動)
「ユーザー」タブの一覧で権限・拠点を選び直します(即時反映。変更は監査ログ「権限変更」に記録)。自分自身の権限は変更できません。

### 退職・異動で使わなくなった場合
**「無効化」ボタン**を押します(即時にすべてのデータが見えなくなります)。
**ユーザーを物理削除しないでください。** 過去の操作記録(誰が更新したか)の表示名が失われるためです。

> 退職者の無効化は、退職日当日に実施してください。月次の棚卸し(§7)でも確認します。

### 最低2名の管理者を維持する
管理者が1人だけの場合、その人がMFA端末を失うとログインできなくなります(§3の緊急手順が必要になります)。管理者は常に2名以上にしてください。

## 2. 拠点・メーカー・販売店マスタの追加

「管理」→「マスタ」タブ。
- **拠点**: コード(英大文字2〜4字。管理番号の先頭になります。例 `SPR`)と名称。**コードは一度決めたら変更しません**(管理番号の一部のため)。使わなくなった拠点は「無効化」。
- **メーカー**: 名称を追加。受付フォームのプルダウンに出ます。
- **販売店**: コードと名称を追加。受付フォームで名称入力時に候補が出ます(マスタにない販売店も手入力で受付可能)。
- 削除ではなく**無効化**してください(過去案件との整合のため)。

滞留アラート日数・個人情報の保持年数・自動ログアウト時間は「設定」タブで変更します。

## 3. パスワード / MFA の再設定

### パスワードを忘れた
1. Supabase ダッシュボード → Authentication → Users → 該当ユーザー → **Send password recovery**。
2. 本人に届いたメールのリンクから、新しいパスワードを設定してもらう(12文字以上)。

### スマホ(認証アプリ)を機種変更・紛失した
1. 管理画面「ユーザー」タブで該当ユーザーの **「MFA再設定」**。
2. 本人が次回ログインした際に、認証アプリの再登録画面が表示されます。
- 本人確認(電話で声を確認する・上長に確認する等)を行ってから実施してください。

### 【緊急】管理者全員がMFAでログインできない
Supabase ダッシュボード → SQL Editor で、対象管理者のMFA登録を削除します(実行者は Supabase の組織管理者のみ)。
```sql
delete from auth.mfa_factors where user_id = '<管理者のUUID>';
```
次回ログイン時にMFAを再登録できます。**実施したら、日時・理由・実施者を記録**し、引継ぎ書の記録欄に残してください。

## 4. バックアップと復元

### バックアップの種類(二重化しています)
| 種類 | 内容 | 頻度 | 備考 |
|---|---|---|---|
| Supabase 標準バックアップ | DB全体 | 日次(Pro以上)/ PITR は有料オプション | ダッシュボード → Database → Backups |
| 自社バックアップ(暗号化) | `scripts/backup.sh` が pg_dump → **age で暗号化** | 日次(GitHub Actions `repair-tracker-backup`) | Secrets 設定が必要。保存先は成果物30日。**長期分は社内ストレージへコピー** |
| 写真・添付(Storage) | バケット `repair-files` | 月次推奨 | ダッシュボード → Storage の S3 接続情報で rclone 等により社内へ同期(最新の公式手順で確認) |

> 暗号鍵(`PII_KEYS`)は**バックアップに含まれません**(DBとは別管理)。バックアップを復元しても、鍵がなければ個人情報は読めません。鍵の保管は [セキュリティ設計書](セキュリティ設計書.md) を参照。

### 自社バックアップの初期設定(1回)
```bash
age-keygen -o backup-private.key        # 出力された "Public key: age1..." を控える
```
- **秘密鍵ファイル(backup-private.key)**は会社の金庫(パスワード管理ツール等)に、2名以上がアクセスできる形で保管。GitHub には置かない。
- GitHub リポジトリの Settings → Secrets and variables → Actions に登録:
  `REPAIR_DATABASE_URL`(DB接続文字列。Session pooler 推奨)、`REPAIR_BACKUP_AGE_PUBKEY`(age公開鍵)。

### 手動バックアップ
```bash
DATABASE_URL='postgresql://...' BACKUP_AGE_RECIPIENT='age1...' ./scripts/backup.sh ./backups
```

### 復元手順(障害時・年1回の訓練)
1. **新しい(空の)Supabaseプロジェクト、または検証用DB**を用意する(本番を直接上書きしない)。
2. 秘密鍵を金庫から取り出し、復元:
   ```bash
   ./scripts/restore.sh backups/repair-YYYYMMDD-HHMMSS.dump.age /path/to/backup-private.key '<復元先DATABASE_URL>'
   psql '<復元先DATABASE_URL>' -f scripts/verify-restore.sql
   ```
3. `verify-restore.sql` の結果で件数を確認し、`first_broken_audit_id` が **空(null)** であること(監査ログが改ざんされていない)を確認。
4. Edge Functions のシークレット(`PII_KEYS` 等)を新プロジェクトにも設定し、個人情報の「表示」が動くことを確認。
5. 本番切替する場合は、フロントの環境変数 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` を新プロジェクトのものに変えて再デプロイ。

## 5. 障害時の対応

| 症状 | 確認すること | 対処 |
|---|---|---|
| 全員ログインできない | https://status.supabase.com の障害情報 / ブラウザのURLが正しいか | 障害ならSupabase復旧待ち。紙の「預り票」で一時運用し、復旧後に入力 |
| 特定ユーザーだけ見えない・入れない | 「ユーザー」タブで有効か、権限・拠点が正しいか | 無効なら有効化、権限を修正 |
| 「MFAが必要です」と出続ける | 認証アプリの時刻ずれ(スマホの自動時刻設定) | 時刻を自動設定に。直らなければ §3 のMFA再設定 |
| 更新が他の人の画面に反映されない | 一覧右上に「● リアルタイム更新中」が出ているか | ページを再読込。出ない場合は社内ネットワークがWebSocket(wss)を遮断していないか確認 |
| 写真が表示されない・アップロードできない | ファイルが画像/PDFで10MB以内か。署名URLの期限切れ(5分)なら再読込 | 画面を再読込。Storage の障害でないか確認 |
| 個人情報の「表示」でエラー | Edge Function のログ(ダッシュボード → Edge Functions → Logs)。短時間に多数表示していないか(10分30件の制限) | 制限は時間経過で解除。鍵エラーなら `PII_KEYS` が正しく設定されているか確認(**鍵を勝手に変更しない**) |
| 「他のユーザーが先に更新しました」 | 正常な競合検知 | 画面の案内どおり最新を読み込み、必要な変更をやり直す |
| 画面が真っ白 | ブラウザのキャッシュ / デプロイ直後 | スーパーリロード。直前のデプロイを疑い、ホスティング側で前のバージョンへ戻す |

不明な障害は、①発生時刻 ②操作したユーザー ③画面に出たメッセージ(個人情報は書かない) を記録して、開発担当者へ連絡してください。

## 6. データの全件エクスポート(ベンダー乗り換え・監査対応)

- **CSV**: 「管理」→「全件エクスポート」。個人情報列はチェックを入れた場合のみ含まれます(出力は監査ログに記録)。
- **SQL(完全なコピー)**: `pg_dump` が標準・最も確実です。
  ```bash
  pg_dump --no-owner --schema=public "$DATABASE_URL" > repair-all.sql      # スキーマ+全データ(個人情報は暗号文のまま)
  ```
  個人情報は暗号化されているため、**移行先でも同じ鍵(`PII_KEYS`)が必要**です。鍵は安全な経路で別途引き継いでください。
- 写真・添付は Storage から別途コピーしてください(§4)。

## 7. 定期作業(詳しい一覧は [引継ぎ書](引継ぎ書.md))

| 頻度 | 作業 |
|---|---|
| 毎月 | ①ユーザー棚卸し(退職者の無効化漏れ)②監査ログ「改ざんチェック」ボタンで異常なし確認 ③不審な大量閲覧の確認(下記SQL)④バックアップが成功しているか |
| 四半期 | 権限棚卸し(各拠点責任者に一覧を確認してもらう)/ 依存パッケージの更新確認 |
| 年1回 | **復元訓練**(§4)/ 暗号鍵ローテーションの要否判断 / ドメイン・証明書・契約の更新確認 |

不審な大量閲覧の確認(SQL Editor で実行):
```sql
select p.display_name, count(*) as reveals
  from public.audit_log a left join public.profiles p on p.user_id = a.actor
 where a.action = 'pii_reveal' and a.at > now() - interval '30 days'
 group by 1 order by 2 desc limit 20;
```
他の拠点と比べて極端に多い人がいれば、本人・上長に業務上の理由を確認します。

## 8. 個人情報の自動匿名化(保持期間)

- 完了(完了日)から**保持年数(既定3年)**を経過した案件は、毎日 03:30(JST)に、エンドユーザーの氏名・電話・住所(暗号文)とマスク値、および販売店担当者名・連絡先が**削除**されます(案件自体と履歴は残ります)。
- 登録状況の確認: `select * from cron.job where jobname = 'purge-expired-pii';`
- pg_cron が使えない環境では、外部スケジューラ(例: GitHub Actions の schedule)から `select public.purge_expired_pii();` を毎日実行してください。
- 手動実行: SQL Editor で `select public.purge_expired_pii();`(戻り値は匿名化した件数)。監査ログに「個人情報の匿名化」として記録されます。
- 保持年数の変更は「設定」タブ。**短縮すると次回バッチで即座に対象が増える**ので注意。

## 9. システム更新(保守開発者向け)

1. 変更はブランチで行い、Pull Request で CI(Lint・型・単体・DB・E2E・脆弱性・シークレット検査)が**すべて緑**になってから統合する。
2. DBの変更は**新しいマイグレーションファイルを追加**する(既存ファイルは書き換えない)。RLS(権限)を弱める変更は、`supabase/tests/10_rls_test.sql` のテストが守っています。変更する場合はセキュリティ設計書も更新する。
3. 本番反映: `supabase db push` → `supabase functions deploy ...` → フロントのデプロイ。
4. 依存パッケージ: `npm audit --omit=dev` で high 以上が出たら速やかに更新。
